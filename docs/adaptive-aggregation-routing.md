# Beacon 在线自适应聚合路由

## 目的与执行边界

新的 `aggregation.adaptive_routing.enabled` 模式只支持 `static_relay`。
Supervisor 注入普通交易，不根据目的分片改变交易类型。源分片照常生成
Relay1、执行源端扣款并达成 PBFT。**只有源区块提交后，在构造 Relay2 时**，
源 leader 才读取当前策略的一份快照，将本块每笔 Relay1 恰好分到以下一路：

- 目的分片在聚合集合内：发送源区块已终局凭据，等待 Beacon 聚合与目标结算；
- 否则：构造并发送普通 Relay2。

交易结构和源区块执行与两条路径的最终选择无关。聚合的凭据是出块后的协议
消息，不是预先注入的另一类用户交易。凭据使用原交易 `ROriginalHash` 作为
logical ID；相同 ID 可跨源端、Beacon 和 Supervisor 的生命周期统计对应。

旧的静态目的分片选择和旧的 CrossShardPayment 实验模式保留，以便复现实验。
自适应模式与静态 destination_shards、batch-only、aggregation-only 及旧的
按注入时间/窗口数量停止聚合配置互斥；新实验不得混用旧模式。

## 三种选择与取舍

1. 离线选定 75%：可作为路由消融实验，但依赖全量工作负载的先验，不能宣称在线适应。
2. 每次窗口封口耗时超过阈值即删冷分片：实现简单，但把正常收集窗口误当过载，
   并且偏冷/偏热不等于聚合收益高低。
3. 本方案：使用**已封口但尚未开始构建的窗口的排队时间**探测 Beacon 拥塞，
   用最近的源区块统计估计聚合收益，发布有版本的目的分片集合。

选用第 3 种。它将拥塞信号、收益选择和数据面交付分开，改变的是新发生的源端
分流，不撤销已经达成源端共识或已交给 Beacon 的付款。

## 拥塞信号与默认参数

冻结等待定义为 `now - oldest_queued_window.SealedAt`。当前已经开始构建/正在
Beacon PBFT 的窗口不再计入等待队列，避免把共识执行时间重复解释为队列等待。
正常的 `max_window_duration_ms` 收集时间也不计入冻结等待。

默认值（实现中允许配置）：

| 参数 | 默认 | 意义 |
|---|---:|---|
| freeze_high_ms | 500 | 等待严格超过 0.5 秒触发降载 |
| freeze_low_ms | 100 | 等待不超过 0.1 秒时满足低水位条件 |
| observation_window_ms | 10000 | 最近收到的源区块统计窗口 |
| cooldown_ms | 10000 | 两次策略变更之间最短间隔 |
| reduction_percent | 25 | 每步调整的目的分片数，占全部分片数的比例，向上取整 |
| min_destination_percent | 25 | 最少保留比例，至少一个目的分片 |
| recovery_window_ms | 2000 | 恢复交易量统计窗，独立于聚合冻结窗口 |
| recovery_windows | 3 | 基准及后续比较各使用的完整统计窗数量 |
| recovery_change_percent | 75 | 相对首降载后基准的绝对涨跌幅，必须严格超过 |

例如 24 分片依次可从 24→18→12→6，每次必须实际观测到过载且满足冷却时间。
恢复时反向增加，要求交易量变化门槛满足、至少 3 次相隔 1 秒的低水位观测及冷却期届满。没有新交易
统计时不进行无依据的策略变化。0.5 秒是当前控制参数，并非由已有静态
实验推导的最优值；必须用新实验检查它是否真的触发和稳定。

冷却时间从上一次策略变更时刻开始计算。第一次降载没有启动冷却期；后续的
降载或恢复都必须相隔至少 10 秒。冷却期内区块构建、Beacon 共识、普通 Relay
及旧批次结算继续执行，不是让交易停止或统一等待 10 秒。
例如 12:00:00 调整 24→18，12:00:03 又检测到排队超限时不立即再减；最早
12:00:10 再次检查仍超限才允许 18→12。控制在收到凭据、每次节点 tick 或尝试构建提案时检查，
受节点调度影响，不承诺在超过阈值的瞬间执行。

恢复采用独立的低水位 0.1 秒，并要求 3 次至少相隔 1 秒的健康观测；仅队列健康不再足以恢复。
显式填写旧阈值 2000ms 的配置仍使用 2 秒；本次默认值修改只作用于新生成的
实验配置及未显式填写阈值的配置，不修改历史结果或正在运行的节点。

## 统计、评分与恢复

首次从全聚合降载后，以连续 3 个完整的 2 秒统计窗中收到的全部正金额跨片
原交易量建立基准 B。源块统计包含当前走 Relay2 的目标，不能把降载后 Beacon
聚合输入自身变少误当成总需求变少。首批基准窗结束后，使用最近 3 个完整且
不与基准重叠的统计窗交易量 R 比较：`abs(R-B)/B > 75%` 才允许考虑恢复。
窗口长度与数量相同，比较总数等价于比较均值或每秒到达速率。

这是用户确认的绝对涨跌幅规则：`R < 0.25B` 或 `R > 1.75B`。变化恰好为 75%
不恢复；涨幅超过 75% 也仍须满足队列低水位及冷却条件。基准为零时不恢复，
不能进行有意义的相对比较。再次降载不会重置同一轮首个基准；恢复到全聚合后
清除本轮统计，下次首次降载重新建立基准。默认最早须收齐 6 秒基准窗和之后
6 秒比较窗，不能用不完整窗口外推。这里的 75% 与聚合目的分片比例无关。

策略 CSV 追加 RecoveryBaselinePayments、RecoveryObservedPayments、RecoveryWindowMs、
RecoveryWindows、RecoveryChangePercent，记录作出策略决策时的基准与比较总数。
收到源回执的本地时间决定窗口归属，数据到达受到网络和节点调度影响；这不是
对未来负载或真实最大处理容量的预测。

控制器以增量计数维护最近 10 秒收益统计：收到新回执时加入，过期时减去，
不会在每次判断重新扫描/复制整个历史。三窗比较使用固定环形缓存及运行总和。
无变化时不生成策略快照，真正切换或到达重播时刻才复制策略。检测调用频率、
阈值和重播间隔保持不变。局部微基准与复现方法见
[`control-overhead.md`](../experiments/adaptive_aggregation/control-overhead.md)。

每个普通分片的源 leader 在每个已提交区块的凭据中附上所有 Relay1 的目的
分片计数与块内不同接收方计数，包括当前走 Relay2 的目的分片。即使当前不
聚合，也能持续观测该目的分片，避免反馈盲区；空区块凭据仍照常发送以维持
源区块水位连续性。

对最近 observation_window_ms 内收到的区块统计，令某目的分片的付款数为 P，
各源区块不同接收方数之和为 U。以 `(P-U)/P` 作为块内可合并收益的保守估计，
从高到低排序；相同收益优先 P 较大者，再按 shard ID 排序，保证稳定。
U 不是跨整个窗口去重的接收方数，因此这是在线收益代理，不假装知道未来
窗口的真实去重率。源块统计仅用于控制，不是资产或终局性证明。

降载在当前启用集合内保留最高评分项；恢复从未启用集合中加入最高评分项。
冷却期内不反复换集合，最少保留配置比例，不允许全关后永远失去观测。
重复/旧源区块统计不重复计入控制样本。阈值滞回和恢复观测约束抑制抖动。

## 控制消息和异步切换

Beacon 固定 leader（node 0）发布 `AggregationRoutingPolicy`，包含单调版本、
所选目的分片、有因果解释的冻结等待、最近统计及调整原因。广播给全部普通
分片副本，并发送给 Supervisor 留存控制日志。当前策略定期重播。

普通节点只接收 Beacon leader 的该类消息，检查 shard ID 范围、重复项和版本。
旧版本忽略，相同版本同内容幂等，相同版本不同集合拒绝。
启动时本地版本 0 表示全聚合；没有全局屏障或必须同时切换的假设。

路由决策对**每个源区块**只做一次，区块交付函数在本轮串行消息处理中完成。
延迟收到策略的源分片可以多聚合若干区块：这影响负载，不影响付款正确性。
Beacon 必须接受并排空旧版本已经选择聚合的凭据，不能再用最新 allowlist
过滤这些付款，也不能给它们补发 Relay2。每份凭据携带源端使用的策略版本。

策略是性能建议，不改变源区块状态转换，不要求把普通分片的外部路由表作为
源 PBFT 验证输入。Beacon 聚合批次仍由现有 PBFT 达成共识，目标结算仍使用
现有 Merkle 证明和批次/分片/chunk 的执行标记保证幂等。

与现有实现相同，消息的 NodeID/源分片身份按测试床配置的 leader 信任约定
处理；这不是新增的密码学身份验证或完整拜占庭源分片证明。进程持久化恢复、
leader failover 后的持久交付日志不在当前测试床既有保证内，本改动不宣称
新增这两类保证。

## Supervisor 与度量

普通 CSV 的零金额交易不属于正金额聚合付款。源块提交后，它们保持原始
封套并固定走 Relay2，仍计入原交易完成数；既不进入聚合证明，也不进入
目的分片收益评分。全聚合对照仅要求所有可聚合的正金额交易始终聚合。
零金额源/目标记录单独计数，动态降载证据只使用正金额 Relay2 的增量，避免
把固定兼容路径误判成策略切换。零金额源块仍发送回执以维持连续水位。

Supervisor 以原交易 hash 跟踪自适应模式中的全部跨片付款。普通 Relay2 的
目标区块消息和聚合已结算完成消息分别完成同一个 ID 空间中的不同子集。
不能因为普通交易池排空就结束实验，必须等待所有已注入跨片付款完成。

聚合源端执行记录只包含实际选择聚合的 Relay1；普通 Relay 统计只接收走
Relay 的 Relay1/Relay2，避免将聚合付款计入未完成 Relay 生命周期。
路由变更单独导出 CSV，记录版本、原因、冻结等待和目的分片集合。
聚合/普通 Relay 完成数据合并后，每个原交易必须恰好出现一次。

## 验证与实验

可控 Beacon 拥塞使用 `experiment_work_us_per_payment`，默认 0。实验中每个
冻结窗口按逻辑原交易数乘以该微秒数增加模拟服务时间，采用非阻塞服务门，
期间仍接收回执与运行控制器。它模拟吞吐容量，不冒充实测 CPU 开销；固定每批
增加时间无法随聚合流量降低而降低负载，因此不采用这种注入方式。

全聚合对照仍使用新普通交易、普通源端扣款和提交后路由路径，保持
`adaptive_routing.enabled=true` 且 `min_destination_percent=100`。同一套件
复用同一批二进制和交易前缀，只有最低聚合目的分片比例与动态组不同。

每次 tick 导出冻结队列等待、排队逻辑原交易数、策略版本与当前目的分片数。
窗口指标另记 `ServiceQueueWaitNs`（开始模拟服务前的等待）以及
`ExperimentServiceTimeNs`；原 `FrozenQueueWaitNs` 为冻结到实际构建的跨度，
在注入实验中包含模拟服务时间。分析降载不能混淆这几个时间，也不能仅用注入
结束后的自然排空作为收益证据。

- 控制器：默认全开；严格高阈值、冷却、在线排序、最少集合、滞回恢复；
  时间采用可注入的 now，测试不靠 sleep。
- 路由表：旧/重复/冲突/非法集合消息；快照不受后续更新影响。
- 凭据：同一源区块的 Relay1 分成两条路径，原交易结构不变，逻辑 ID、金额
  和源区块 hash 保持；空聚合凭据仍保留连续水位。
- 集成：控制消息传递到普通节点，冻结老窗口继续排空，新源区块按新策略分流。
- Supervisor：混合完成、重复消息、乱序完成不会提早结束。
- `go build ./...`、完整 Go 测试、依赖整洁检查和可用 lint；至少一次 4×4
  加 4 Beacon 副本的真实本地实验，验证全量完成、无重复和错误日志。
- 静态 24/75% 的旧图是旧路由消融结果，不能替代动态方案的控制时序实验。

实际运行入口与已完成的 4×4 验证结果见
[`experiments/adaptive_aggregation/README.md`](../experiments/adaptive_aggregation/README.md)。
